Getting Started

Prerequisites

  • Node.js 20+
  • pnpm 9+ installed globally
  • Git

Tech Stack

React 19 Vite TanStack Router TanStack Query Tailwind CSS v4 shadcn/ui better-auth WebSocket

Setup

Terminal
git clone https://github.com/zartis-digital/x-clone-starter cd x-clone-starter pnpm install

Environment Variables

Create a .env file in the project root to point the frontend at the workshop API:

.env
VITE_API_URL=<workshop-api-url> VITE_WS_URL=<workshop-ws-url>
The real values above will be shared closer to the workshop date, once the backend is deployed. This page will be updated in place — no need to re-clone. Unlike some other starters, there's no separate storage URL to configure: the API already returns full, ready-to-use image URLs, so the frontend never builds one itself.

Then start the dev server:

Terminal
pnpm dev

App runs at http://localhost:5173. Launch Claude Code with claude in the project root.

Project Structure

src/ routes/ ← File-based routing (TanStack Router) components/ tweet/ ← Tweet card, composer, reply box, actions ui/ ← shadcn/ui primitives hooks/ ← Custom hooks (WebSocket client, etc.) lib/ ← API client helpers, timeline cache queries/ ← TanStack Query option factories stores/ ← Client-side state
Important: The backend API is already deployed and fully functional. You only work on the frontend during this workshop.

Guardrail Hooks — Block Risky File Access
Stop Claude reading secrets or editing generated files
~10 min

Hooks are commands Claude Code runs automatically on lifecycle events, with no model involved. They live in .claude/settings.json and receive a JSON payload on stdin. Before we build anything, let's use them as guardrails — a PreToolUse hook can inspect a tool call and block it, giving you a hard guarantee that a scoped rule can't. We'll write them as small Node scripts so they run on every machine — macOS, Linux, and Windows — with no jq and no shell quirks. (Hooks are also one of the three extension points — more on that in Part 2.)

1. PreToolUse — don't read secrets
Prompt
First use the claude-code-guide agent to check the documentation on how to create hooks. Then add a PreToolUse hook that blocks Claude from reading secret files like .env, .env.local, and .env.production, with a clear reason — but still allow the safe .env.example template. Write it as a cross-platform Node script so it runs on macOS, Linux, and Windows.
2. PreToolUse — don't write lockfiles or generated files
Prompt
First use the claude-code-guide agent to check the documentation on how to create hooks. Then add a PreToolUse hook that blocks Claude from editing lockfiles and generated files like pnpm-lock.yaml and src/routeTree.gen.ts, with a reason explaining it's a lockfile or a generated file. Write it as a cross-platform Node script so it runs on macOS, Linux, and Windows.
Why Node + exec form? Setting "command": "node" with an args array spawns the script without a shell, and Claude Code substitutes ${CLAUDE_PROJECT_DIR} itself — so the same hook runs identically on macOS, Linux, and Windows, with no jq, Git Bash, or WSL. A shell one-liner would need a POSIX shell on Windows.
Hooks run code as you — only add hooks you trust. The Read guard covers the Read tool; Claude could still cat .env via Bash, so for airtight secrets also use Claude Code's built-in permissions.deny (e.g. "Read(./.env)"). Run /hooks to see what's active.
Reference: the .claude/settings.json (exec form)
.claude/settings.json
{ "hooks": { "PreToolUse": [ { "matcher": "Read", "hooks": [ { "type": "command", "command": "node", "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/deny-read-env.mjs"] } ] }, { "matcher": "Edit|Write", "hooks": [ { "type": "command", "command": "node", "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/deny-write-protected.mjs"] } ] } ] } }
  • Reading .env is blocked with a clear reason
  • Editing pnpm-lock.yaml / routeTree.gen.ts is blocked
  • Hooks run unchanged on your OS (exec form, no jq)

Writing good requirements is a dialogue, not a monologue. This skill does the product work directly in your main thread — where it can actually ask you questions — so there's no separate "product manager" agent to maintain.

I want to create a skill called interview-requirements that acts as a product manager to flesh out a feature before filing an issue. Create Issue Skill
A /create-issue slash command that saves issues to docs/issues/
~5 min

Skills live in .claude/skills/<name>/SKILL.md and automate repeatable workflows. A skill can be invoked manually as /name or chosen automatically by Claude. The /create-issue skill gives you (and any agent) a standard way to persist requirements as markdown files you can pick up and implement later.

Prompt
I want to create a skill called create-issue that turns a feature, bug, or task into a tracked work item. When I run /create-issue, it should read a title and short description from the arguments, generate a URL-friendly slug from the title (lowercase, hyphens, no special chars), and create a markdown file at docs/issues/<slug>.md with these fields: title, description, acceptance criteria, priority (low/medium/high), and status: open. It should create the docs/issues/ directory if it doesn't exist and print the path of the created file. After creating the file, offer next steps: suggest implementing the issue we just created (referencing the file path) or creating another issue. Only let me invoke it manually, not the model, and give it just the tools it needs to write the file.
A skill runs in the current conversation context. Anything — you, the interview skill, or the QA agent — can invoke /create-issue directly, making it a shared contract for the requirements workflow.
Test the hand-off

Once the skill is created, run it with a test feature and watch the hand-off in action:

Claude Code
/create-issue "Dark Mode Toggle" "Add a dark/light mode switch that persists the user's preference in localStorage."

After creating the file, Claude should offer next steps naturally — something like:

Expected output (example)
Created docs/issues/dark-mode-toggle.md Next steps: - Implement the issue we just created → docs/issues/dark-mode-toggle.md - Create another issue
The hand-off keeps momentum: instead of dropping the user back at a blank prompt, the skill points them at the obvious next action — implement what was just specced, or keep filing issues.
Document the convention

The skill knows where issues live, but the main thread doesn't yet — so prompts like “implement the next open issue” or a QA agent filing bugs have nothing to anchor on. Record the convention in CLAUDE.md (always-on context) so every session and every agent shares it.

Prompt
Add a short "## Issue tracking" section to CLAUDE.md documenting our convention: tracked work items live in docs/issues/<slug>.md as markdown with a status field that goes from open to done. They're filed with /create-issue and resolved with /close-issue. Keep it to a couple of lines.

Close Issue Skill
A /close-issue skill that marks an existing issue done — closing the loop opened by /create-issue
~5 min

Where /create-issue writes a brand-new file, this skill reads and mutates an existing one — the other half of file-manipulation skills. It completes the requirements lifecycle: interview → open → build → QA → close.

Prompt
I want to create a skill called close-issue that marks a tracked work item as done. When I run /close-issue with an issue slug (or part of a title) in the arguments, it should find the matching file in docs/issues/, flip its status field from open to done, and append a short resolution note plus the current commit reference if I provide one. If no slug matches, or several do, it should list the candidates and ask me which one rather than guessing. After updating, it should print the file path and a summary of which issues are still open. Only let me invoke it manually, not the model, and give it just the tools it needs to read and edit the files.
Like /create-issue, this is a shared contract — you can close an issue by hand once a feature passes review, or have the QA agent reference it. Notice it teaches Read + Edit (finding and changing state), the counterpart to /create-issue's Write.

  • Ran /close-issue on an open issue and saw its status flip to done

QA Agent
A testing agent that verifies features and reports bugs
~5 min

Agents (subagents) are specialized helpers that Claude delegates work to. Each is a markdown file in .claude/agents/ whose frontmatter defines its role, tools, and a description Claude uses to auto-delegate (or you ask for it by name). Crucially, a subagent runs in its own separate context window — it doesn't see the main conversation; it does its job and returns a result.

QA is the role where that isolation actually pays off. Because it runs in a separate, fresh context, it reviews the feature with fresh eyes — exactly what the main thread that just built it is bad at. It tests implemented features using Chrome DevTools MCP, checks both happy path and error states, and files bug reports as new issues to fix. A review/QA subagent like this is the standout real-world subagent pattern.

Prompt
Create a QA agent at .claude/agents/qa.md. Give it a frontmatter description that triggers auto-delegation (e.g. "QA tester. Use proactively after a feature is implemented to verify it and file bug reports."). Restrict its tools so it can test but never modify source — no Edit/Write: tools: Read, Grep, Glob, and add the Chrome DevTools MCP server (via the mcpServers frontmatter field) so it can drive the browser. It should: - Test features by navigating the app with Chrome DevTools MCP (take screenshots, click buttons, fill forms) - Check both happy path and error states - Verify responsive behavior at mobile and desktop widths - Report bugs by creating a new issue via /create-issue with: steps to reproduce, expected vs actual behavior, and a screenshot path - Never fix bugs — only report them clearly for the developer to fix
Know the limits: a subagent gets a fresh context window (it can't see your current conversation), it cannot call other subagents — chain them from the main thread instead — and it cannot use AskUserQuestion, which is exactly why the interactive /interview-requirements step stays in the main conversation, not inside an agent.

Try the full workflow (a learning exercise):

Prompt
Run /interview-requirements 'the ability to pin a tweet to your profile' to spec the feature, then save it with /create-issue. Implement the issue yourself in the main thread. Finally, use the QA agent to test it and report any issues.
Reality check: this product→dev→QA chain is a sequential pipeline — each step depends on the last, so information leaks in the handoffs. It's a great way to exercise the agent/skill mechanics, but in real work you'd keep dependent, iterative work (like implementation) in the main thread and reserve subagents for the standalone wins: research, fresh-eyes review, and custom-prompt tasks.
Agent vs Skill — when to use which?
Agents delegate a self-contained task to a separate context window with its own role and tools — use them when you want focused work done in isolation (e.g., a QA tester vs a developer) and just the result back. Skills are one-shot automations that run in the current conversation — use them for repeatable tasks like gathering requirements, creating issues, or committing.

Codebase Explorer Agent
A read-only research agent that answers "how does X work?" without flooding your context
~5 min

The QA agent showed one reason to reach for a subagent: restricting its powers. This one shows the other — context isolation. Answering "how does a like flow from the UI to the API?" means opening a handful of files, but you only care about the answer. Delegate it and the agent spends its fresh context budget on all that reading, then hands back a tight summary — your main thread stays clean for the work that actually needs it.

Where QA runs after a feature to verify it, you'll reach for the explorer during the build — before changing code you don't yet understand.

Prompt
Create a codebase explorer agent at .claude/agents/codebase-explorer.md. Give it a frontmatter description that triggers auto-delegation for research questions (e.g. "Read-only codebase researcher. Use when answering a question requires reading across many files — tracing a data flow, locating where something is implemented, or summarizing how a subsystem works — so the main thread stays uncluttered."). Restrict its tools to read-only exploration: tools: Read, Grep, Glob — no Edit, Write, or Bash. It should: - Search broadly to answer the question, reading only the relevant excerpts rather than whole files - Trace data flow across layers (components → queries → API) and identify the key files - Return a tight, structured summary of its findings with exact file:line references — never a dump of everything it read - Never modify code or run the app — only investigate and report back
Two agents, two different payoffs: qa trades on restricted tools + fresh eyes, the explorer on a separate context budget. Both are read-only reporters — the pattern that suits subagents best — and neither can ask you questions, which is why interactive work stays in the main thread.

Part 5: Tips, Tricks & Resources

Useful patterns, keyboard shortcuts, and links to keep learning.

Tips & Tricks

Prompting

  • Be specific about files — "In src/components/tweet/tweet-actions.tsx, add a bookmark button" works better than "add a bookmark button somewhere".
  • Ask Claude to check the actual API response — there's no interactive API reference published yet, so "hit this endpoint and show me the response shape before you write code against it" replaces what a Swagger doc would otherwise give you.
  • Iterate, don't restart — If Claude gets something wrong, tell it what's wrong in the same conversation. It has full context of what it just did.
  • Paste error messages — Copy-paste the full error. Claude is great at diagnosing stack traces and TypeScript errors.
  • Use screenshots — "Take a screenshot and tell me what's wrong" is a powerful debugging prompt when you have Chrome DevTools MCP configured.

Workflow

  • Plan Mode for complex features — Use Shift+Tab to toggle Plan Mode before starting a multi-file feature. Review the plan, then toggle back to execute.
  • One feature per conversation — Start a new conversation (/clear) between features to keep context clean and focused.
  • Compact long conversations — If a conversation gets long, use /compact to summarize the history and free up context space.
  • Let the agent cook — For big features, give Claude the full requirements and let it work. Review the result rather than micromanaging each step.
  • Use agents for different hats — Switch to the QA agent after implementing a feature to catch bugs you might have missed.

Keyboard shortcuts

  • Shift+Tab — Toggle Plan Mode
  • Esc — Cancel current generation
  • Tab — Accept Claude's suggestion
  • Ctrl+C — Exit Claude Code

Useful links

  • Claude Code Documentation — Official docs covering installation, configuration, CLAUDE.md, MCP servers, agents, and more
  • Anthropic Skilljar Courses — Free courses on prompt engineering, Claude best practices, and building with Claude

Reference: WebSocket Events

The backend pushes live updates over a single WebSocket connection. All engagement events are count-only — the client patches the relevant tweet in the TanStack Query cache rather than refetching.

Event Payload
tweet.like_updated tweetId, actorId, likeCount
tweet.retweet_updated tweetId, actorId, retweetCount
tweet.reply_added parentTweetId, actorId, replyCount
